# Landing page performance — CHAM Brightening Face Mask

**Why this was measured:** Meta reports only 55–67% of link clicks becoming
landing page views. A healthy figure is roughly 80%+.

## The pixel is not the cause

Events Manager, dataset `2840657352995594`, Oct 11 – Nov 7:

| Event | Count | Source | Match quality |
|---|---|---|---|
| PageView | 2.8K | Multiple | 6.3/10 |
| View content | 1.6K | Multiple | 6.3/10 |
| Add to cart | 548 | Multiple | 6.5/10 |
| Initiate checkout | 77 | Multiple | 7.1/10 |
| Contact | 55 | Meta Pixel | — |
| Add payment info | 14 | Multiple | 7.6/10 |

PageView fires in volume, which is what a landing page view counts.

Earlier in this work I twice reported seeing no `facebook.com/tr` PageView
beacon on the storefront. That was wrong: the beacon is sent from Shopify's
sandboxed web-pixel frame, which neither top-frame resource timing nor the
browser extension's network log can see. Events Manager is the authority.

Instagram's in-app browser also checks out: `fbclid` survives into the URL, the
`_fbc` cookie is written from it, `fbq` is defined, and there is no redirect
chain on the landing URL beyond the normal http→https hop.

## The cause is main-thread load after first paint

Three Lighthouse runs, mobile, simulated throttling, 2026-11-08:

| | run 1 | run 2 | run 3 |
|---|---|---|---|
| Performance score | 64 | 71 | 58 |
| Total Blocking Time | 2,140 ms | 1,180 ms | 1,620 ms |
| LCP | 2.5 s | 2.4 s | 3.4 s |
| Style & Layout | 6,074 ms | 5,136 ms | 4,997 ms |
| Script Evaluation | 5,075 ms | 3,595 ms | 5,151 ms |

Time to Interactive ~16 s. 327 requests, 1,088 DOM elements, 153 KB unused JS.

The page paints at ~2.5 s and is then unresponsive for roughly twelve more
seconds. On a mid-range Android inside Instagram's in-app browser on a Pakistani
mobile network, that is where clicks are lost: the visitor leaves before
PageView fires, so Meta counts the click and no landing page view.

### On comparing with the 2026-11-06 run

That run showed TBT 510 ms and score 79, which looks like a large regression.
Do not treat it as one. Between the two runs, execution time rose by a similar
factor for third parties nobody touched — `fbevents.js` 226→543 ms, Judge.me
500→707 ms, Shopify perf-kit 171→532 ms. Lighthouse's simulated throttling
calibrates against the host CPU, so a busier machine inflates everything. The
two runs are not comparable.

What *is* established is that the current state is poor in its own right: TBT
1.2–2.1 s across three consecutive runs, none close to the 200 ms target.

## Where the time goes, in priority order

1. **Inline `<script>` on the document — the largest single contributor.**
   Lighthouse attributes 5.0–7.8 s to the page URL itself, which means inline
   script tags rather than external files. About 30 KB of inline JS runs on this
   page: `layout/theme.liquid` (16 KB), `sections/main-product.liquid` (6 KB),
   plus the video-row, regimen and WhatsApp snippets. 30 KB costing seconds means
   repeated DOM and layout work, not parse cost.
2. **Style & Layout, ~5 s.** 1,088 DOM elements against a large stylesheet.
   The theme uses `color-mix()` in 157 places and `backdrop-filter` in 14.
3. **Judge.me review widget**: 707 ms of script and roughly 100 requests, loaded
   during first render rather than when scrolled into view.
4. **153 KB of unused JavaScript**, plus 13 KB of legacy transpiled code.

## Not yet verified

Whether any single one of these, fixed in isolation, moves the click-to-landing
-page-view rate. Each should be measured with three runs before and after, given
how noisy single runs are on this machine.

## Judge.me release guard — measured

`layout/theme.liquid` now holds back Judge.me's runtime-inserted scripts and
`<link>` preloads on the product template until the reviews are within 1,200px
of the viewport (or on a `#reviews` deep link, or where IntersectionObserver is
missing). Verified on an unpublished theme: 7 Judge.me requests on load instead
of 104; nothing renders with the reviews 3,000px away; with them 900px away all
104 load, 68 review cards render, and the widget height is 1,350px, identical to
before. The Product/aggregateRating/Review JSON-LD is server-rendered by the app
block and is unaffected.

Interleaved Lighthouse A/B, live vs guard, mobile, simulated throttling, 8 runs
per arm (medians):

| | live | guard |
|---|---|---|
| Style & Layout | 5,927 ms | **3,417 ms** (-42%) |
| Script Evaluation | 3,234 ms | 2,647 ms (-18%) |
| Total Blocking Time | 817 ms | 652 ms (-20%) |
| Requests | 340 | 279 (-18%) |
| Performance score | 73 | 73 |

Read this soberly. Style/layout and request count fell clearly. TBT improved but
the runs overlap heavily (one guard run hit 3,095ms), and the composite score
did not move. Do not expect this change alone to fix the landing-page-view rate.

### What it does not fix: the Meta pixel loads last

Time to interactive stays near 16s in both arms even with Judge.me held back.
The late long tasks in the guard arm are Facebook's own `fbevents.js` and
`signals/config` scripts, ~18-19s into the throttled timeline. Shopify's web
pixel manager loads the Meta pixel late under CPU contention, which is outside
the theme's control. Landing page views are counted from when that pixel fires,
so on slow phones the pixel may be firing after a good share of impatient
visitors have already left. Adding a second Meta base pixel to the theme would
double-count against the app's pixel and add a script, so it is not proposed.

### A first version of the guard had a timer fallback

It released Judge.me 15s after load. That landed the whole burst of widget work
in the middle of the page's lifetime for a visitor who never scrolled to the
reviews, so it was removed. The Lighthouse TTI difference it was blamed for turned
out to be the Facebook scripts above, not Judge.me.

### Other measured facts worth keeping

- The LCP image is a 19KB WebP, eager and high-priority, fetched in 37ms. The LCP
  breakdown shows ~1,080ms of "element render delay": the image is downloaded and
  the main thread is too busy to paint it.
- ~340 style recalcs in 11s with no script on the stack, in rendering frames: the
  page keeps invalidating style while idle. Not yet attributed.
- `polish.js` runs a document-wide MutationObserver that re-scans every image 120ms
  after any DOM change (47 scans in 11s). Small (17ms native) but wasteful.
- `main-product.liquid`'s `addToCart()` is dead code; see DEPLOYMENT-STATE.md.

## Idle style recalcs — cause found and fixed

The page produced ~250-300 style recalcs in 11s with no script on the stack.
Two hypotheses were tested and rejected before the real cause was found:

- **The announcement-bar marquee** (from the admin Custom CSS box, not the theme
  files): stopped on the preview theme, recalc count was unchanged (196-281 with it
  on, 248-272 off).
- **`polish.js`'s MutationObserver**: ~17ms native, not worth touching.

The cause: Shopify's own `/checkouts/internal/preloads.js` `prefetch()` appends
about 160 `<link rel="prefetch">` elements to the page, one every ~55ms, and 160
of the ~290 scheduled recalcs trace back to it. That alone is cheap, but
`critical.css` and `whatsapp-float.liquid` carried `html:has([data-drawer-open])`
rules, and a `:has()` anchored on `<html>` is re-evaluated on every DOM insertion
anywhere in the page. Removing the rules left the recalc count the same and made
each one about five times cheaper.

Fix: the scroll lock is now `html[data-drawer-open="true"]`, and the drawer code
sets that attribute on `<html>` next to the `<body>` one it already set
(`assets/cart-drawer.js`, `layout/theme.liquid`). The `dialog/details[scroll-lock]`
half of the old rule matched nothing in this theme.

Same-environment before/after, full traces on the preview theme, native time:

| | before | after |
|---|---|---|
| Style recalc time | 747 / 591 ms | **119 / 92 ms** (-85%) |
| Layout time | 228 / 214 ms | 168 / 168 ms |

Lighthouse A/B, live vs fix, 4 runs per arm, medians (both carry the Judge.me guard):
style and layout 2,631 -> 1,092 ms (-58%), LCP 2,228 -> 1,887 ms, FCP 1,415 -> 1,332 ms.
**TBT (549 vs 630), score (81 vs 77) and TTI (14.2 vs 17.2s) did not improve.** Style
recalcs are many short tasks, so they barely register in TBT, which counts only
tasks over 50ms. The preview arm is also penalised on the late-long-task metrics:
it loads Shopify's preview-bar scripts and ~19 more requests than live. Treat this as
a real reduction in CPU work (less battery and heat on a phone) and a small LCP gain,
not as a score improvement.

## LCP — what was tried and why nothing shipped

The simulated LCP on this page swings between roughly 1.8 and 4.8s from run to run
on identical code, so anything under ~0.5s cannot be seen without many runs.

Already optimal, from fresh live runs: the hero image is `fetchpriority=high`,
discoverable in the initial HTML, not lazy-loaded, a 19KB WebP, the server answers in
0.04-0.19s, there are no redirects and no render-blocking resources. The only long
critical chain is Shopify's own Shop Pay modules (~0.5s, not on the LCP path).

**Tried: preloading the hero image from the head. No gain, reverted.**

- Hypothesis: the `<img>` sits after a ~113KB head (mostly Shopify-injected), so the
  browser only discovers it late; a preload near the top of the head would start the
  request sooner.
- It was wrong. Observed time from first byte to the image request starting stayed at
  ~0.24s with the preload in place, equal to the HTML document's own download time
  (0.32-0.43s). Shopify delivers the page as one unit, so nothing can be discovered
  before it has fully arrived, preload or not.
- The first version also made things worse. It sat above the viewport meta tag, which
  is emitted by `snippets/meta-tags.liquid`. `imagesizes` is in vw, and before the
  viewport tag is parsed a phone is treated as 980px wide, so the preload picked the
  1800w file while the `<img>` later asked for 800w: two downloads, 25KB wasted, and
  simulated LCP 3.03s vs 2.81s on live. A desktop browser showed one request and hid
  the problem; it only appeared under mobile emulation.

A/B, 5 runs per arm (medians, simulated): live LCP 2.81s, preload build 3.03s, with
the duplicate. After moving it below the viewport tag there was a single 800w request
and no gain.

Do not retry a head preload of the hero. The one real remaining lever on LCP from the
theme is the weight of the HTML document itself (~71KB over the wire; ~314KB raw, ~113KB
of it head), since its download time is what gates image discovery.

# Landing page performance — CHAM Brightening Face Mask

**Why this was measured:** Meta reports only 55–67% of link clicks becoming
landing page views. A healthy figure is roughly 80%+.

## The pixel is not the cause

Events Manager, dataset `2840657352995594`, Oct 11 – Nov 7:

| Event | Count | Source | Match quality |
|---|---|---|---|
| PageView | 2.8K | Multiple | 6.3/10 |
| View content | 1.6K | Multiple | 6.3/10 |
| Add to cart | 548 | Multiple | 6.5/10 |
| Initiate checkout | 77 | Multiple | 7.1/10 |
| Contact | 55 | Meta Pixel | — |
| Add payment info | 14 | Multiple | 7.6/10 |

PageView fires in volume, which is what a landing page view counts.

Earlier in this work I twice reported seeing no `facebook.com/tr` PageView
beacon on the storefront. That was wrong: the beacon is sent from Shopify's
sandboxed web-pixel frame, which neither top-frame resource timing nor the
browser extension's network log can see. Events Manager is the authority.

Instagram's in-app browser also checks out: `fbclid` survives into the URL, the
`_fbc` cookie is written from it, `fbq` is defined, and there is no redirect
chain on the landing URL beyond the normal http→https hop.

## The cause is main-thread load after first paint

Three Lighthouse runs, mobile, simulated throttling, 2026-11-08:

| | run 1 | run 2 | run 3 |
|---|---|---|---|
| Performance score | 64 | 71 | 58 |
| Total Blocking Time | 2,140 ms | 1,180 ms | 1,620 ms |
| LCP | 2.5 s | 2.4 s | 3.4 s |
| Style & Layout | 6,074 ms | 5,136 ms | 4,997 ms |
| Script Evaluation | 5,075 ms | 3,595 ms | 5,151 ms |

Time to Interactive ~16 s. 327 requests, 1,088 DOM elements, 153 KB unused JS.

The page paints at ~2.5 s and is then unresponsive for roughly twelve more
seconds. On a mid-range Android inside Instagram's in-app browser on a Pakistani
mobile network, that is where clicks are lost: the visitor leaves before
PageView fires, so Meta counts the click and no landing page view.

### On comparing with the 2026-11-06 run

That run showed TBT 510 ms and score 79, which looks like a large regression.
Do not treat it as one. Between the two runs, execution time rose by a similar
factor for third parties nobody touched — `fbevents.js` 226→543 ms, Judge.me
500→707 ms, Shopify perf-kit 171→532 ms. Lighthouse's simulated throttling
calibrates against the host CPU, so a busier machine inflates everything. The
two runs are not comparable.

What *is* established is that the current state is poor in its own right: TBT
1.2–2.1 s across three consecutive runs, none close to the 200 ms target.

## Where the time goes, in priority order

1. **Inline `<script>` on the document — the largest single contributor.**
   Lighthouse attributes 5.0–7.8 s to the page URL itself, which means inline
   script tags rather than external files. About 30 KB of inline JS runs on this
   page: `layout/theme.liquid` (16 KB), `sections/main-product.liquid` (6 KB),
   plus the video-row, regimen and WhatsApp snippets. 30 KB costing seconds means
   repeated DOM and layout work, not parse cost.
2. **Style & Layout, ~5 s.** 1,088 DOM elements against a large stylesheet.
   The theme uses `color-mix()` in 157 places and `backdrop-filter` in 14.
3. **Judge.me review widget**: 707 ms of script and roughly 100 requests, loaded
   during first render rather than when scrolled into view.
4. **153 KB of unused JavaScript**, plus 13 KB of legacy transpiled code.

## Not yet verified

Whether any single one of these, fixed in isolation, moves the click-to-landing
-page-view rate. Each should be measured with three runs before and after, given
how noisy single runs are on this machine.
